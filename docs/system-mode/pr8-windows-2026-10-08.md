## LDPlayer target and preparation

LDPlayer 14.0.9.2, Android 14/API 34, x86_64 with 4 KiB pages, permissive SELinux, ext4 root at
`/dev/block/sda2`. The observed fingerprint SHA-256 is
`1c5673700ed4dc77aebb82cd8d2230b281678a7801324cf0b68eca0c876bdb58`.

The user-owned instance 0 was externally backed up, challenged with a marker, restored with
verified offline image/configuration hashes, boot-checked with its original released manager/root,
and stopped. Lifecycle work then moved to the newly created `KitsunePR8-20261008` instance 1.
MuMu Android 15 was excluded throughout.

The disposable instance required explicit preparation:

- `basicSettings.standaloneSysVmdk=true` provides its own writable system image. The factory
  shared system image remains read-only even with vendor root enabled.
- The original system filesystem had approximately 24 MiB free. The maintained debug APK is
  40,550,699 bytes and is retained in the persistent payload for recovery. Its attempted install
  failed with ENOSPC, rolled back, removed the transaction/payload, and retained the original policy
  digest. The host qualifier now rejects a candidate whose persistent payload lower bound cannot fit.
- Only the disposable VDI was expanded to 3 GiB. The final MBR partition retained its start sector
  26,514; its length became 6,264,942 sectors. Online ext4 growth produced 783,117 blocks and about
  515 MiB free. This is a prepared-image result, not stock-image space compatibility.
- LDPlayer's Superuser settings activity crashed with an invalid `PolicyNativeFragment`. A
  temporary vendor-root policy was granted only to the hash-verified Next manager's UID in the
  device-protected vendor policy database. Root was then verified from the app's own context.
- The unmodified vendor `ldinit` removed Magisk's `su` aliases when vendor root was disabled.
  Magisk remained running, but its public `su` entry points disappeared and boot verification failed.
  The disposable baseline now uses the same exact 11-byte anti-scrub change produced by the user's
  LDPlayerRoot tool. Original `ldinit` SHA-256:
  `4bee5b7c7f024b1aef224f3ca32472d940a59a331daedf90ba044f7ab709cb95`;
  prepared SHA-256:
  `2fec61399bdc2947a9106fd27823ecdaaa1c6ac0ecbd388b87cb44be86239af0`.
  Ownership, mode and `u:object_r:ldinit_exec:s0` were retained.

Preparation belongs to the emulator adapter and is included in the external recovery image. It is
not a new native Magisk hook or a claim that an arbitrary stock LDPlayer version is supported.

## Observed maintained-line results

The final prepared target completed the machine qualifier's three distinct cold boots, init and
Magisk-domain execution proofs, challenged system/data backup restore, and clean backup restore.
The LDPlayer identity projection tolerates vendor metadata rewrites while binding the UUID,
hardware identifiers, private media layout, controller and ADB endpoint. Generic file identity
remains unchanged.

System Mode then committed through the manager and its one-shot host lease. After boot it reached
`BOOT_VERIFIED`. Vendor `su` was removed only after matching its recorded SHA-256, and the vendor
root setting was disabled. Three subsequent cold boots retained `uid=0`, `u:r:magisk:s0`, the exact
`31.0-kitsune-next.99ab2c55:MAGISK:D` runtime, `BOOT_VERIFIED`, and absence of the vendor `su`.
An idle, unprivileged `pidof magiskd` observed one daemon; querying from inside an active `su`
request also sees its temporary broker and must not be misreported as a second persistent daemon.

The Shell policy denied access before approval and granted root after the manager's Superuser
switch was enabled. Immediate repeated toggle/request timing is not a complete revoke-latency
qualification; that remains part of the policy matrix.

The minimal module passed installation, post-fs-data execution, visible `/system/etc` content,
disable, re-enable, and removal across cold boots. An unrelated `/data/adb` sentinel survived.

Reinstall qualification exposed one additional host-comparison defect: Magisk regenerates
`/data/adb/sepolicy.rule` on boot with identical bytes but a new mtime. The qualifier now retains
that raw timestamp while comparing all policy bytes and security metadata. A regression proves
that changed bytes, size, permissions, ownership or labels still fail comparison.

The same exact APK then passed reinstall through a new one-shot lease and cold-booted to
`BOOT_VERIFIED`, preserving the unrelated sentinel. This establishes same-version reinstall;
it is not a separate-version upgrade result. A concurrent SU run passed all 48 requests with
eight clients, and the idle sample returned to one daemon.

The APK-owned uninstall backend completed with exit 0 in its private mount namespace, restored
the original precompiled-policy digest, removed the owned system and rescue payloads, and kept
the unrelated sentinel and emulator preparation. The enclosing SU connection closed when the
daemon stopped; the script's own completion and postconditions were captured separately.
Manager-UI complete-uninstall and a post-uninstall cold boot were not established by this run.
The complete external prepared snapshot was then restored and all offline hashes verified.

## MuMu Windows target

MuMu Global 6.8.0 Android 12 instance 2 (`KitsunePR8-20261008`) was created separately from
the user's existing instance 1. Android 15 instance 0 remained stopped. The disposable target
uses API 32, x86_64, 4 KiB pages, permissive SELinux, an ext4 system partition and a private
difference image over the vendor's read-only base. Its controller-reported ADB port is 16448;
the fingerprint SHA-256 is `bc138f6be66e4234dbb37e86ca84e3f7e33f2c6259c1a6d8ff15e7035c433a98`.

MuMu rewrites even its MAC identity file at boot. The explicit `mumu-v1` identity now binds the
vendor metadata and backing chain, with seven regressions covering rewrites, tampering, foreign
attachments/endpoints, Android 15 exclusion and capture races. Qualification then exposed a
recreated ramdisk `/sepolicy` copy: its bytes and security metadata matched exactly across boots,
but its mtime changed. A focused regression preserves every other policy check. With those host
fixes, the target passed three init/Magisk-domain cold boots, challenged restore and clean restore.
The clean external snapshot and sealed record are retained. The exact Next APK installed through
the manager and reached `BOOT_VERIFIED`. Three subsequent vendor-root-off cold boots retained
that state, `uid=0` in `u:r:magisk:s0`, the exact `99ab2c55` version and one idle daemon. On this
configuration the owned `su` alias is under `/system/xbin`; its target matched the installed
Magisk binary, rather than the vendor client.

The standard module passed install, post-fs-data, visible file, disable, re-enable and removal
checks across cold boots. The unowned `/data/adb` sentinel survived. Shell was denied before its
Superuser switch was enabled; afterward all 48 requests with eight concurrent clients passed.

Reinstall qualification stopped before guest writes: the image had 43,515,904 bytes available,
below the 47,713,785-byte candidate payload lower bound. The existing installation remained
`BOOT_VERIFIED`. This stock-capacity target is not a successful reinstall/upgrade result.

The manager's **Complete uninstall** removed its APK and stopped the daemon. A pre-positioned
read-only observer confirmed removal of the owned system/rescue payloads, preservation of the
unowned sentinel, and the original vendor policy SHA-256
`438989426d2f1200db8ec9e06861cff39e3346e89650c40f42c7920bbfa2e4f5`.
The subsequent cold boot reached Android with no manager APK, daemon, runtime binary or working
`su`. The read-only observer result survived that boot. Full external restore then verified all
offline image/configuration hashes and returned the clean vendor-root baseline.

The current-line `b416c8dd` APK was installed on that same restored baseline. Its original host
authorization protocol used the sealed qualification's actual backup/init/cold-boot facts. It
failed at `Normalize Magisk runtime metadata`, as on LDPlayer. The full UI log was captured;
rollback removed the init/system/data payload and preserved the original vendor policy digest.
Another complete external restore passed and the disposable MuMu instance was stopped.

One expired lease and one not-yet-valid lease were rejected before installation. The latter was
caused by a guest clock approximately 31 seconds behind the host; waiting within the existing
five-minute lease allowed the unchanged artifact to proceed. The lifetime check was not weakened.
MuMu's rendered advertisements can cover dialogs without appearing in UI Automator's tree;
visual confirmation and dismissal were necessary before the root and policy UI checks.
